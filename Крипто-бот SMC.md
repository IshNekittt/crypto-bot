# УЛЬТИМАТИВНЫЙ АРХИТЕКТУРНЫЙ МАНИФЕСТ: BYBIT SMC-BOT (V5 API)

Мульти-пара с изолированными инстансами (Worker/Actor pattern), задаваемая через `.env` `SYMBOLS=SOLUSDT,BTCUSDT,ETHUSDT`.
Одновременная торговля на 3-5 парах сглаживает кривую доходности.
Техническая реализация: Бот должен иметь один общий Risk Manager (который следит за общим балансом) и массив независимых Strategy Engine (каждый подписывается на свои WebSocket-каналы и ведет свой State Machine).

## 0. МЕТА-ИНСТРУКЦИЯ ДЛЯ ИИ-РАЗРАБОТЧИКА

Ты — Senior Node.js / Quant разработчик и SDET-инженер. Твоя задача — написать полностью автономного торгового бота для криптобиржи Bybit (деривативы Linear Perpetual), торгующего по концепции Smart Money (SMC).

**Ограничения:**

1. Никакого хардкода сумм, символов и задержек. Все параметры тянутся из Bybit API и `.env`.
2. Библиотеки: `bybit-api` (официальная), `decimal.js` (вся математика денег), `winston` (логи), `better-sqlite3` (БД), `telegraf` (или native fetch) для Telegram.
3. Тотальная обработка отказов (Network failures, API Rate Limits, WS disconnects).
4. Строгая типизация TypeScript. Никаких `any`.

## БЛОК 1: ИНФРАСТРУКТУРА И ИНИЦИАЛИЗАЦИЯ (BOOTSTRAP)

При старте (`npm start`) бот обязан выполнить Pre-flight Checks:

1. **Sync Time:** Синхронизировать время локальной машины с сервером Bybit (`GET /v5/market/time`), чтобы избежать ошибки _Timestamp for this request is outside of the recvWindow_.
2. **Fetch Instrument Info:** Сделать запрос `GET /v5/market/instruments-info` для списка торгуемых пар (из `.env`). Сохранить в кэш критические параметры: `tickSize` (шаг цены), `qtyStep` (шаг лота), `minOrderQty`.
3. **Set Leverage/Margin:** Принудительно установить тип маржи Isolated и плечо (например, 10x) через `POST /v5/position/set-leverage` для каждой пары. _(Важно: плечо влияет только на обеспечение, риск управляется лотностью!)_.

## БЛОК 2: ДОМЕННЫЕ МОДЕЛИ И ЖЕСТКАЯ SMC-МАТЕМАТИКА

Используем паттерн "Чистой архитектуры". Модуль математики не знает про Bybit, он принимает массивы. Все расчеты через `Decimal`.

1. **Candle:** `{ timestamp, open, high, low, close, volume }`.
2. **SwingPoint:** Экстремум (High/Low). Логика: свеча является максимумом, если ее `high` выше 3-х свечей слева и справа.
3. **FVG (Imbalance):** `gap = Candle[3].low - Candle[1].high` (для лонга). Если `gap < 0.1%` от цены — игнорируем (шум).
4. **OrderBlock (OB):** Последняя противоположная свеча перед импульсом (BOS/ChoCh), сломавшим структуру.
5. **ЖЕСТКАЯ ЛОГИКА (Smart Money):**
   - **BOS/ChoCh (Слом структуры):** Считается валидным ТОЛЬКО если свеча 15m **закрылась телом** (`close`) выше Swing High (для лонга) или ниже Swing Low (для шорта). Прокол тенью (wick) — не считается.
   - **Импульс:** Свеча, сломавшая структуру, должна иметь тело `Math.abs(open - close)`, которое минимум в **2 раза больше** среднего значения тел последних 10 свечей (Average True Body).
   - **Инвалидация OB:** Если цена закрывается телом (`close`) ниже Low 4H Order Block (для лонга) — зона считается пробитой (Invalidated), стейт-машина сбрасывается в SCANNING.
   - **Установка уровней (SL и TP):**
     - **SL_Price:** Устанавливается на 0.1% ниже (для лонга) или выше (для шорта) экстремума 15m Order Block, от которого ищется вход.
     - **TP_Price:** Рассчитывается динамически строго как 1:3 от риска. `TP = Entry + ((Entry - SL) * 3)`. Никаких ручных тейков.

## БЛОК 3: ИСТОЧНИКИ ДАННЫХ (ГЛАЗА БОТА)

Архитектура требует двух независимых потоков данных:

1. **REST Исторический билдер:** При старте бот скачивает по 200 свечей 4H и 15m через `GET /v5/market/kline`.
2. **Public WebSocket (Цена):** Подписка на `wss://stream.bybit.com/v5/public/linear`. Топики: `kline.15.{symbol}` И `kline.240.{symbol}` (4H).
   - _Сшивание:_ Массивы таймфреймов ведутся независимо. Когда приходит пакет с флагом `confirm: true` (свеча закрыта), она добавляется в массив, выбивая самую старую свечу (`shift()`).
3. **Private WebSocket (Исполнение):** Подписка на `wss://stream.bybit.com/v5/private`. Топики: `execution` и `position`. Бот узнает о срабатывании Stop Loss не из расчетов, а напрямую от биржи.

## БЛОК 4: STATE MACHINE (МОЗГ СИСТЕМЫ)

Каждая пара запускается в своем инстансе со следующими статусами:

1. **SCANNING:** Поиск 4H Order Block. Найден? -> Переход в WAITING.
2. **WAITING:** Ожидание касания ценой зоны 4H OB.
   - _Anti-Stuck:_ Если касания нет 30 свечей (4H), статус сбрасывается в SCANNING.
3. **CONFIRMATION:** Внутри зоны 4H ждем Liquidity Sweep + ChoCh на таймфрейме 15m. После ChoCh ищем свежий 15m FVG и 15m OB.
4. **ENTRY_STAGED:** Отправка Telegram-алерта о найденном сетапе. Ждем отката в 15m FVG. При касании — запуск Execution Engine. Переход в IN_TRADE.
5. **IN_TRADE:** Бот ничего не анализирует. Ждет эвента от Private WS о закрытии позиции. При получении эвента -> SCANNING.

---

## БЛОК 5: ДИНАМИЧЕСКИЙ РИСК-МЕНЕДЖМЕНТ (ЩИТ)

Расчет строго перед отправкой ордера (на этапе ENTRY_STAGED):

1. **Опрос баланса:** `GET /v5/account/wallet-balance` (баланс USDT).
2. **Базовый риск:** Значение из `.env` `RISK_PERCENT` (например, 2% от баланса на сделку).
3. **Kelly Criterion / Drawdown guard:** Если последние 3 сделки были убыточными (чек по локальной базе), риск режется до 1%. После профита возвращается к базовому.
4. **Расчет лота (Qty):**
   - `SL_Distance = Math.abs(Entry_Price - SL_Price)`
   - `Raw_Qty = (Balance * (Risk_% / 100)) / SL_Distance`
5. **Bybit Precision Formatter:**
   - `Qty` должен быть округлен кратно `qtyStep` (вниз!).
   - `Price`, `SL`, `TP` должны быть округлены кратно `tickSize`.
     Если после округления `Qty < minOrderQty`, сделка отменяется (недостаточно средств).

## БЛОК 6: EXECUTION ENGINE И TELEGRAM АЛЕРТЫ

**Формирование ордера** через `POST /v5/order/create`. Никаких ручных закрытий! Бот делегирует стопы бирже:

- `category`: "linear", `orderType`: "Market", `tpslMode`: "Full", `timeInForce`: "IOC".
- `qty`: Строка после форматтера, `stopLoss` / `takeProfit`: Строки после форматтера.

**Модуль Telegram-уведомлений:**
Интеграция с Telegram API (переменные `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`). Отправка сообщений в случаях:

- **ENTRY_STAGED:** "👀 Найден сетап по {Symbol}. Вход: {Price}, SL: {SL}, TP: {TP}".
- **IN_TRADE:** "🚀 Ордер открыт по рынку!".
- **TRADE_CLOSED:** "✅/❌ Позиция закрыта. PnL: {Pnl} USDT".
- **КРИТИЧЕСКИЕ ОШИБКИ:** API Rate Limits, дисконнекты, ошибки маржи.

**Circuit Breaker (Анти-слив):** При получении 3 ошибок _Insufficient Margin_ или _Rate Limit_ подряд, бот останавливает торговлю этой парой на 1 час и шлет Alert в Telegram.

## БЛОК 7: БЕЗОПАСНОСТЬ И ВОССТАНОВЛЕНИЕ (RESILIENCE)

1. **Local State DB (better-sqlite3):**
   - **КРИТИЧНО:** База обязана инициализироваться с флагом `PRAGMA journal_mode = WAL;`. Так как у нас Worker/Actor паттерн для разных пар, WAL-режим предотвратит ошибки `SQLITE_BUSY` (database is locked) при конкурентной записи логов сделок по разным парам.
   - Хранить историю сделок и текущий статус стейт-машины каждой пары.
2. **Reconciliation Loop (Аудит):** Каждые 10 минут бот дергает `GET /v5/position/list`.
   - Если бот думает, что он `IN_TRADE`, а на бирже позиции нет (стоп сработал, а WS отвалился) -> принудительный сброс стейта в SCANNING.
3. **WS Auto-Reconnect:** Встроенный механизм heartbeat (ping/pong каждые 20 сек). При разрыве соединения — переподключение и перевызов логики Bootstrap (Блок 1).
